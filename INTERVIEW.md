# Interview questions: timelock

## Q1. Why add a timelock on top of a multisig? What does each one protect against, and what can still go wrong with both in place? Use test_TwoStolenKeysStoppedByGuardian.

Answer: A multisig protects against one key being lost or stolen, because no single owner can act alone, while a timelock protects against the approvers themselves being wrong or compromised, because it gives people time to see an approved action and react. A multisig alone fails once two keys are stolen, since the attacker meets the 2-of-3 threshold and nobody gets any time to respond. `test_TwoStolenKeysStoppedByGuardian` shows this: Bob's and Carol's keys queue `setFee(9999)`, and the multisig treats it as valid. Executing straight away reverts with `NotReady`, the guardian then cancels during the delay, and executing two days later reverts with `NotQueued`, so `feeBps` stays 0. The test only ends well because the guardian acted, so a guardian who is offline or not watching lets the action run once the delay ends. A cancel is also not permanent, so attackers holding two keys can queue again, and they can use `MultiSig.replaceOwner`, which has no delay, to remove the honest third owner. Finally, a stolen guardian key can cancel every action, and because `guardian` is immutable it can never be replaced.

## Q2. Walk through an action's life cycle in my Timelock. Why is there a grace period, why can anyone execute, and why must setDelay go through the queue?

Answer: The multisig calls `queue`, which checks that the caller is the admin, computes the ID from the target, value, data and salt, and stores `readyAt[id] = block.timestamp + delay`. During the delay the action is public through the `Queued` event, and the admin or guardian can `cancel` it. From `readyTime` through `readyTime + GRACE_PERIOD` (14 days), `execute` checks the timing, deletes the entry, emits `Executed` and makes the call, and if the call fails the whole transaction reverts, so the action stays queued and can be retried. The grace period makes approvals go stale, so an action approved long ago cannot be run much later when conditions have changed. Anyone can execute because the decision was already made at queue time and the ID ties the caller to the exact action, so the caller only chooses when it runs, and offline keys cannot strand an approved action. The cost is that the caller picks the moment within the window, so actions that are only safe at a certain time or in a certain order should not be queued this way. `setDelay` only accepts `msg.sender == address(this)` because otherwise two stolen keys could immediately cut the delay to the 1-hour minimum before queuing anything else, whereas going through the queue makes that change wait out the current delay and gives the guardian a chance to cancel it.

## Q3. I changed the ID hash to use data.length instead of data and all 24 tests stayed green. Why was that a critical bug, why did the tests miss it, and what does that say about test coverage?

Answer: `getId` is what ties an approval to a specific action, and with `data.length`, `setFee(100)` and `setFee(9999)` get the same ID because both are 36 bytes. Since `execute` is public and only checks the ID, any stranger could wait for an honest action to become ready and then run different calldata of the same length, with the timelock as the caller. That made the multisig's approval and the guardian's review meaningless for the action's contents, because what they saw in `Queued` was not necessarily what ran. The 24 tests missed it because each one executed with exactly the data it queued, and the same input still produces the same ID, so the bug never changed a result. This shows that coverage only tells you code ran, not that a test would notice it behaving wrongly. Useful coverage tests the property that only the exact queued action can run, including negative cases such as `test_RevertWhen_DataDiffersFromQueued`, which fails with the bug and passes with the fix. Deliberately breaking the code, known as mutation testing, checks whether the tests are able to fail at all, and changing `data` to `data.length` is exactly that kind of mutation.

## Q4. OpenZeppelin's TimelockController had CVE-2021-39167 before 4.3.1: execute checked isOperationReady only after the call. How could an executor take over, and which lines of my execute prevent that kind of attack?

Answer: Before the fix, `execute` and `executeBatch` ran the calls first and checked `isOperationReady(id)` only afterward, so an operation could make itself ready while it was running. An executor could submit an unscheduled batch whose calls, made with the timelock as the caller, set the minimum delay to zero, grant the proposer role to an attacker's contract, and have that contract schedule the same batch with zero delay. When the batch finished the check passed, and the same batch could also grant the attacker admin and revoke other members' roles, giving full control of the contract and its assets. The fix added a readiness check before the calls and kept the one after them, because without it an executor could run a batch several times through reentrancy. In my `execute`, lines 68-70 check that the action is queued, ready and unexpired before the call at line 77, so an unqueued action reverts before any of its calls run. Line 73 also deletes `readyAt[id]` before the call, so re-entering with the same ID reverts with `NotQueued`, which is why I do not need a second check after the call. An action also cannot schedule itself, because `queue` is admin-only (line 52) and the timelock is not its own admin. This ordering matters even more in my contract, because `execute` is open to everyone rather than limited to an executor role, so the same mistake would let any caller attempt the attack.

## Q5. In the Beanstalk attack there was a one-day wait, yet the attacker still took the funds in one transaction. Why didn't the wait help, and where must a delay sit? What are the trade-offs of a long delay, for example in an emergency?

Answer: Beanstalk's `emergencyCommit` let a 2/3 supermajority execute a proposal after 24 hours, so the attacker submitted malicious proposals and simply waited that time out. The wait came before the decision, and voting power was not flash-loan resistant, so one transaction could borrow enough to reach about 79% of the votes, pass the proposal, execute it, drain the funds and repay the loan. The attack cost the protocol about $181 million, of which the attacker kept about $76 million. A delay must sit after the final approval and before execution, and voting power should be fixed before a proposal exists, because a flash loan has to be repaid in its own transaction and so cannot last through a delay. My Timelock follows this order: `queue` records the approval, and `execute` can only succeed in a later transaction at least an hour afterward. A longer delay gives the guardian and users more time to react or exit, but it also slows legitimate actions, including urgent fixes, and during a live exploit my contract cannot speed anything up because the guardian can only cancel and there is no pause. Emergency bypasses have their own risk, since Beanstalk's was the path the attacker used. A safer design limits fast powers to defensive actions like pausing or cancelling, rather than letting them execute arbitrary code.
